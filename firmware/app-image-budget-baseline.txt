# MeshCadet firmware app-image size baseline — see
# xtask/src/partition_budget.rs and firmware/partitions.csv's `factory`
# partition comment.
#
# The single non-comment line below is the app-image size in BYTES, as
# produced by firmware/scripts/measure-app-image-size.sh (a release build +
# `esptool elf2image`, same artifact firmware/release-container/build.sh
# publishes as the app-only update artifact). `cargo run -p xtask --bin
# xtask -- verify-partition-budget` recomputes this figure fresh from a real
# build every time it runs and fails loudly if it has drifted more than 5%
# from the value below — see that check's module doc for why this exists:
# firmware/partitions.csv used to carry the equivalent number as hand-written
# "measured" prose in a comment, which had no recompute trigger and silently
# decayed 2.72 MB stale as the tree grew, undetected across an entire
# campaign's worth of flash-budget decisions (see
# meshcadet-emoji-font-upgrade-checkpoint-20260802-140922469).
#
# METHOD — read this before comparing this number against any other
# app-image figure in the campaign record. This value is the byte count of
# the `esptool elf2image` output, i.e. exactly what
# measure-app-image-size.sh prints. That is NOT the same quantity as the
# sum of loadable `PT_LOAD` `FileSiz` from `xtensa-esp32s3-elf-readelf -lW`,
# which is how the milestone-2 gate and the render-set-contract mission
# reported their figures. Measured on one identical ELF at commit cd08085,
# the two differ by -1.61% (elf2image 3,360,432 B vs. PT_LOAD sum
# 3,415,374 B) — elf2image omits segments that need no flash backing. The
# gap is under the +-5% drift threshold on its own, but it is roughly a
# third of the whole drift budget, so do NOT seed this file from a
# readelf-derived number: always take it from measure-app-image-size.sh (or
# verify-partition-budget's own "measured" line).
#
# The first version of this file got exactly that wrong: it carried
# 5,083,402 B, which was the milestone-2 gate's readelf-derived figure,
# while documenting it as "produced by measure-app-image-size.sh".
#
# PREVIOUS baseline — measured 2026-08-02 at commit cd08085 (a direct
# `xtensa-esp32s3-espidf` release build + elf2image, by
# meshcadet-emoji-coverage-flash-budget-recompute-20260802-161907805):
#
#   3,360,432 B (3.20 MiB) of the 6 MiB (6,291,456 B) `factory` partition,
#   2,931,024 B (2.80 MiB) headroom — 53.4% used.
#
# Why it moved -33.9% from the previous 5,083,402 B entry: that entry was
# measured at 1abad3e, and FOUR firmware-affecting merges landed after it
# (#134 ui_task split, #135 the 7x-embedded-backdrop dedupe, #136 the
# render-set contract's 50 seed codepoints, #137 this guard itself). The
# dominant term is #135, which recovered 6 redundant copies of a
# 300,480-byte backdrop = -1,802,880 B. Reconciliation against the same
# readelf method the old value used: 5,083,402 -> 3,415,374 = -1,668,028 B
# observed, vs. -1,802,880 (dedupe) + 94,768 (#136) = -1,708,112 predicted;
# the +40,084 B residual is #134 plus sdkconfig changes.
#
# NOTE: the previous entry's own comment asserted it was "confirmed still
# current ... since `git diff 1abad3e..HEAD -- firmware/ ...` is empty".
# That was true on the branch that wrote it and false on `main` within
# hours — the branch simply predated those four merges. A staleness claim
# pinned to the author's own branch tip is not a staleness claim about
# main; this guard's whole point is that only a fresh build settles it.
#
# PREVIOUS baseline — measured 2026-08-02 by
# meshcadet-emoji-render-set-curation-20260802-141020550, which grew
# `RENDER_EXTRA_CPS` from 50 to the campaign's confirmed 600-entry target
# (+550 codepoints):
#
#   4,348,560 B (4.15 MiB) of the 6 MiB (6,291,456 B) `factory` partition,
#   1,942,896 B (1.85 MiB) headroom — 69.1% used.
#
# Moved +29.40% from the 3,360,432 B previous entry (+988,128 B for 550 new
# render-only codepoints = ~1,796 B/entry average), consistent with the
# render-set-contract mission's measured 1,814-1,947 B/emoji marginal cost —
# comfortably inside this mission's own +998-1,071 KB budget and under the
# 4,718,592 B (4.5 MiB) hard ceiling, with ~370 KB of margin still under it.
#
# CURRENT baseline — measured 2026-08-23, sourced from the failing CI
# `firmware` job's own `verify-partition-budget` step run at this branch's
# head commit cf450fb0fe08e6eadc45b8d20b2426071726dc44
# (https://github.com/jagoda/meshcadet/actions/runs/32655143768/job/97232591655),
# by ci-fix-meshcadet-lock-firmware-ui-20260823-174742559. NOT a local

# by the identical script, on the identical tree — is used as the freshest

#
#   4,641,888 B (4.43 MiB) of the 6 MiB (6,291,456 B) `factory` partition,
#   1,649,568 B (1.57 MiB) headroom — 73.8% used.
#
# Moved +6.75% from the 4,348,560 B previous entry (past the 5% threshold,
# which is exactly why CI failed and this baseline needed bumping). This PR
# (jagoda/meshcadet#179) lands the screen-lock overlay + lock screen
# (4-dot pad + numpad reusing pin_entry.rs's theme, D4 backoff countdown,

# drift to chase down.
#
# Expect a few bytes of run-to-run noise even on an unchanged tree: two
# consecutive builds at cd08085 measured 3,360,432 B and 3,360,448 B (16 B
# apart). measure-app-image-size.sh deliberately skips the release build's
# SOURCE_DATE_EPOCH / --remap-path-prefix reproducibility flags (see its
# header), so byte-exact equality is not expected — which is precisely why
# this guard has a +-5% band rather than an equality check. Do not chase a
# sub-kilobyte delta.
#
# Bump this value ONLY after `verify-partition-budget` reports a drift you've
# confirmed is a real, intentional change to the app image (new UI assets,
# new glyph coverage, a dependency upgrade, etc.) — never to silence a
# failure without reading why it moved. Derive the new value by actually
# running firmware/scripts/measure-app-image-size.sh (or reading
# `verify-partition-budget`'s own "measured" line), never by hand-editing
